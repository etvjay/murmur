Why Murmur

Private money shouldn't depend on a network someone can switch off.

Murmur carries a real shielded Zcash transaction and a sealed note from device to device.

Whoever reconnects first broadcasts it, and the payment confirms on chain.

Offline build

The payer's wallet creates, proves and signs a shielded transaction with no connection at all. Only the final raw transaction leaves the device, never the partly built file that can hold viewing keys.

Sealed notes

Notes and receipts are sealed to one recipient. The sender's key is mixed into the key derivation, so a forged sender is rejected. Verified in tests.

Try the simulation

Over a cap, the wallet is never asked to sign.

Spend policy

Caps per payment and while offline, plus an optional recipient list. The policy bounds double-spend risk. It does not remove it.

See the limits

Example shape. A request like this was paid on the testnet, block 4,550,881. The memo was not observed on chain.

Payment request

A merchant shares a ZIP 321 request. The payer's command reads the address, amount and memo from it, then builds the payment. One was paid on the testnet in block 4,550,881; the memo did not show up on chain.

Three runs, all logged. A builds a transaction offline. B carries one across and confirms it. C pays a ZIP 321 payment request end to end.

      
Run A: built with the network cut

      
The build ran in a network namespace with no connection. A lookup of the wallet server failed there first, as required. Then every step of the transaction build succeeded.

      
  • create
  • prove
  • sign
  • combine
  • extract

      
  • Raw transaction20,986 bytes, unified-address recipient
  • BroadcastNo. This run stops before broadcast by design.
  • Log folderevidence/03-acceptance-a

      
Run B: across the carrier and onto the chain

      
A payer process built the transaction and sent it with a sealed receipt. A separate gateway process received both, broadcast the transaction once and sent back a sealed acknowledgement. Both ran on one machine over UDP loopback, so this run did not use a radio.

SHA-256 printed by the payer and by the gateway. Identical, so the bytes crossed unchanged.

      

      
Run C: a payment request, paid

      
The merchant made a ZIP 321 request. The payer's wallet built the payment with every devtool step inside a no-network namespace (a probe there fails with a DNS error), handed it to a gateway over loopback UDP, and the gateway broadcast it once. The acknowledgement and the receipt carry the sender's key.

∟memo.case[✳]
not verified
The memo in a payment request. It was passed to the build, but did not show up in either wallet's view of the confirmed transaction. Whether it was dropped or just not displayed is not determined.
evidence/05-zip321-e2e

    
∟expiry.case[✳]
limit
An offline transaction expires about 50 minutes after the wallet's last sync: the default expiry is 120 blocks since NU7, at 25-second blocks. One built against a stale tip carried expiry 4,550,721 and was refused at height 4,550,785. Sync before going offline.
Observed on the testnet

    
∟change-notes.case[✳]
not supported yet
Offline signing through the devtool's PCZT path cannot spend change notes (SaplingVerify(WrongFvkForNote)). The native send can. The real run paid from an account holding an externally received note.
evidence/05-zip321-e2e/attempt-1-change-note-sign-failure

    
∟radio.case[✳]
not run yet
A laptop and a phone exchange a message over a real Wi-Fi link.
scripts/acceptance-b.md

    
∟multihop.case[✳]

∟bluetooth.case[✳]
not built
Bluetooth transport. It needs a native app.
Out of scope

    
∟authentication.case[✳]
what it does not give
Sender authentication is not proof that a key belongs to a person, and a relay can still drop, delay or replay a genuine packet.
Threat model

    
∟double-spend.case[✳]
double-spend
A payer can still spend the same notes elsewhere before broadcast. The spend policy limits the loss. Nothing here makes offline settlement trustless.
Threat model

    
∟observer.case[✳]
observer view
Anyone watching sees packet sizes, timing and neighbors, and that a shielded transaction exists. Not the payer, the recipient or the amount.
